# 자기소개서

> 복잡한 업무 화면을, 다음 사람이 안심하고 고칠 수 있게 만드는 프론트엔드 개발자 이현도입니다.

## 1. 성장 과정

### 숫자를 맞추던 사람이, 해결책을 만드는 사람으로

경제학을 전공하며 현상을 변수와 제약으로 나눠 보는 훈련을 했습니다. 재경관리사와 회계관리 자격을 준비하면서는
숫자가 맞지 않을 때 원인을 끝까지 따라가는 습관이 생겼습니다. 다만 분석보다 **직접 해결책을 만드는 일**에 더
끌렸고, 2022년 애드인에듀의 자바 풀스택 과정(React · Spring Boot)에서 개발을 시작했습니다.

과정 중 진행한 그룹웨어 프로젝트에서 인사 · 이메일 기능을 설계부터 프론트엔드 · 백엔드까지 맡았습니다.
Elasticsearch 로 인사 통계를 시각화하고, 메일 서버 없이 SMTP 로 실제 송수신을 구현했습니다. 이때 처음으로
"동작하는 기능"과 "믿고 쓰는 기능"은 다르다는 것을 배웠습니다. 주민등록번호를 화면에 보이기 전에 마스킹하는
처리를 직접 넣으면서, 사용자가 신경 쓰지 않아도 되게 만드는 것이 개발자의 몫이라고 생각하게 됐습니다.

## 2. 직무 역량

### 화면 너머의 계약까지 책임지는 프론트엔드

첫 회사 토피도에서 2년 4개월 동안 공공 · 금융 SI 프로젝트에 참여했습니다. ESB 관리 콘솔의 프론트엔드를
맡았고, 농협 세금계산서와 한국도로공사 프로젝트에서는 백엔드 코드도 직접 고쳤습니다. 서버가 데이터를 왜 그런
형태로 주는지 아는 경험은, 지금 API 계약을 먼저 맞추는 방식의 바탕이 됐습니다.

현재 코드넛에서는 7개월 동안 네 개의 고객사 프로젝트에 참여했고, 그중 두 개는 프론트엔드를 혼자 맡았습니다.

- **설계:** 모노레포 구조와 Feature-Sliced Design 을 적용했고, 설계 결정 17건을 ADR 로 남겼습니다.
- **계약:** OpenAPI 명세에서 타입을 생성하고, 명세와 코드가 어긋나면 CI 에서 먼저 깨지게 했습니다.
- **복잡한 UI:** CodeMirror 6 기반 JSON 편집기, 선언형 레이아웃 체계, 실시간 미리보기 탭을 구현했습니다.
- **품질 · 배포:** 경계 테스트, Vitest · Playwright, Docker · Kubernetes 배포까지 직접 구성했습니다.

## 3. 문제 해결 경험

### "여러 사람이 고쳐도 아무것도 잃지 않게" — 교재 에디터

**상황.** 티처스 클래스의 교재 에디터는 레이아웃 수십 종과 칸마다 다른 글자 수 한도를 다뤄야 했고, 여러
관리자가 같은 차시를 동시에 고칠 수 있었습니다. 처음 구조에서는 레이아웃이 늘 때마다 에디터, 미리보기, 가이드
문서를 따로 고쳐야 했고, 에디터에서 만든 교재를 수업 Player 가 미리보기와 똑같이 재생해야 하는 과제도 있었습니다.

**해결.** 레이아웃을 화면 코드가 아니라 **데이터(선언)** 로 정의하고, 폼 · 도움말 · 글자 수 한도 · 가이드 페이지가
모두 그 선언에서 만들어지게 바꿨습니다. 교재 렌더러는 독립 패키지로 빼서 에디터와 수업 화면이 같은 코드로
그려지게 했습니다. 동시 편집 문제는 편집 잠금, 저장 충돌 창, 판 기록과 되돌리기, 새로고침 복원으로 막았습니다.

**결과.** 레이아웃 추가 작업이 선언 하나를 쓰는 일로 줄었고, 미리보기와 실제 수업 화면은 같은 코드로 그려져
어긋날 여지가 없어졌습니다. 이 경험으로 "문제를 고치는 것"보다 "문제가 다시 생길 수 없는 구조를 만드는 것"을 먼저 생각하게
됐습니다.

### "운영 환경의 제약 안에서" — HRD-Net 온프렘 배포

한국산업인력공단 포털은 운영본이 공단 내부 온프렘 서버에 있고, 내부망이 PATCH · DELETE 요청을 막았습니다.
수정 한 줄도 다른 회사 담당자의 재배포가 필요한 환경이었습니다. 차단된 요청은 POST 로 바꾸고, 학습자 화면과
관리자 화면 사이의 import 금지 규칙을 테스트로 검사해 실수가 들어올 틈을 줄였습니다. 배포본은 개발 · v2 · 온프렘
브랜치로 나누고 공통 수정은 cherry-pick 으로만 옮기는 규칙을 문서로 남겼습니다. 테스트는 76개에서 245개로
늘렸습니다.

## 4. 협업 경험

### 합의는 문서로, 약속은 코드로

해봄 AI 플랫폼에서는 백엔드 개발자와 저장소를 나눠 일했습니다. 공유 모듈 없이 **REST 계약만 공유**하기로 정하고,
공개 API 스키마에서 타입을 자동 생성해 서버 변경이 화면에 바로 드러나게 했습니다. 덕분에 서로의 코드를 기다리지
않고 병렬로 개발할 수 있었습니다.

매쓰캔버스에서는 코드 리뷰 문화가 자리 잡힌 팀에서 일했습니다. 리뷰에서 받은 지적(중복 호출 방지, 예외 흐름,
타입 가드)은 항목마다 반영 커밋으로 나눠 무엇을 어떻게 고쳤는지 추적할 수 있게 했습니다. 프로젝트를 마칠 때는
부팅 순서부터 작업별 체크리스트까지 담은 인수인계 문서를 남겨, 다음 담당자가 첫날부터 막히지 않게 했습니다.

## 5. 성격의 장단점

### 장점 — 끝까지 추적하고 기록하는 꼼꼼함

원인을 모른 채 넘어가는 것을 불편해합니다. 버그를 고칠 때는 재현 조건과 원인을 확인한 뒤 수정하고, 그 판단을
커밋 메시지와 ADR 에 남깁니다. 그래서 몇 달 뒤 저나 동료가 같은 코드를 볼 때 "왜 이렇게 됐는지"를 다시 찾지
않아도 됩니다.

### 단점 — 완성도 욕심에 혼자 오래 붙잡는 경향

완성된 상태로 보여 주고 싶어서 혼자 오래 붙잡고 있던 때가 있었습니다. 지금은 작업을 작은 단위로 커밋하고, 설계
선택지가 생기면 구현 전에 먼저 공유해 방향을 맞춥니다. 혼자 맡은 프로젝트에서도 결정을 ADR 로 먼저 적어 두고
리뷰를 받는 방식으로 보완하고 있습니다.

## 6. 입사 후 포부

### 한 사람의 속도를 팀의 속도로

지금까지 프로젝트마다 공통 컴포넌트와 디자인 토큰, API 계약 패키지, 경계 테스트 같은 기반을 직접 세워 왔습니다.
입사 후에는 먼저 서비스의 화면과 도메인을 빠르게 익혀 맡은 기능을 안정적으로 내놓겠습니다. 그다음에는 제가
쌓아 온 기반을 팀 전체가 쓰는 표준으로 다듬어, 동료들이 같은 실수를 반복하지 않고 사용자에게 보이는 화면 자체에
집중할 수 있는 환경을 만드는 개발자가 되겠습니다.
